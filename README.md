# TANBOX CRM

Локальная CRM: React/Vite, Express, PostgreSQL, Telegram и Gemini/OpenAI.

Адрес панели: **http://127.0.0.1:3050**. Порт backend доступен только внутри Docker-сети. Для Windows выбран IPv4, поскольку в этой среде воспроизводились зависания IPv6 localhost через WSL.

## Полная база знаний

Раздел `/knowledge` содержит полные материалы по 12 направлениям, поиск, языки, исходные редакции, источники и экспорт. Полный документ открывается по собственному URL `/knowledge/documents/:id`. В Telegram: «База знаний» → категория → материал → страницы полного текста. Старые правила менеджеров доступны по `/knowledge/rules`.

Интернет-база `/knowledge/web` содержит реестр официальных источников Казахстана и ЕАЭС, оригиналы и историю документов, полнотекстовый поиск, матрицу 18 товарных направлений и общих требований. Первые 17 проверенных утверждений подключены к ответам ИИ; непроверенные тексты и OCR отделены от опубликованных правил. Фоновое обновление включено в production, очередь и ошибки видны в CRM. Это начальный корпус с обозначенными пробелами. Устройство, обслуживание и оставшиеся работы: [KNOWLEDGE_WEB_OPERATIONS.md](KNOWLEDGE_WEB_OPERATIONS.md).

На основе пяти содержательных клиентских обращений добавлены подсказки для повторного контакта, обсуждения цены, расчёта, склада и местного производителя. Они применяются к черновикам ответов в вебе и Telegram, не заменяют правовые основания и не содержат персональных данных исходных клиентов. Разбор и 30 сценариев приёмки: [CLIENT_CONVERSATION_REVIEW.md](docs/knowledge/CLIENT_CONVERSATION_REVIEW.md), [CLIENT_ACCEPTANCE_CASES.md](docs/knowledge/CLIENT_ACCEPTANCE_CASES.md).

Позже изучены четыре уникальных PDF с КП и прайсом, проверены оформление, суммы и соответствие опубликованным настройкам цен. Добавлены сценарий и кнопка «Оборудование и обучение», ограничения для ставок «от» и индивидуальных условий. Индивидуальные цены КП не перенесены в общий контекст ИИ. Результаты и черновики повторного контакта: [COMMERCIAL_OFFER_REVIEW.md](docs/knowledge/COMMERCIAL_OFFER_REVIEW.md).

В карточке клиента → «Расчёт стоимости» работает серверный калькулятор по публичному прайсу TANBOX: ступени, карточки, сопровождение, дополнительные услуги и явно указанная скидка. История хранит версии и использованные ставки; выбранный пригодный расчёт доступен помощнику в вебе и Telegram. Коды оператора, склад и брокер не включены в итог. Подробности: [COMMERCIAL_CALCULATOR.md](docs/knowledge/COMMERCIAL_CALCULATOR.md).

В PostgreSQL сохраняются исходные файлы побайтно, полный JSON и текст каждого материала, все поисковые разделы и история снимков. Обрезка по длине промпта не применяется к хранению. Проверка целостности отдельно сверяет SHA-256 исходников и документов, их количества и сборку полного текста из разделов. Проверка хранения не заменяет правовую проверку содержания; материалы проекта помечены SOURCE.

Воспроизводимый перенос материалов из соседнего проекта маркировки:

```powershell
node scripts/prepare-knowledge-bundle.cjs
docker compose build
docker compose run --rm --no-deps migrate
docker compose run --rm --no-deps backend node dist/knowledge/import.js
docker compose up -d --wait
docker exec tanbox_crm_backend node dist/knowledge/import.js --verify
```

Скрипт читает только перечисленные материалы из `../tanbox` и публичный API тарифов. Другой каталог передаётся первым аргументом. Секреты, базы клиентов, backups, node_modules и Git в снимок не включаются. Если исходники меняются во время подготовки, подготовка завершается ошибкой. JSON `backend/data/knowledge-bundle.json` переносится вместе с приложением; повторный импорт идемпотентен, предыдущие снимки сохраняются.

Кнопки «Проверить полноту хранения» и «Полный экспорт» доступны в вебе. Экспорт включает исходные байты в Base64 и позволяет повторить импорт с тем же хешем. Все исходники и документы требуют авторизации. Обычный backup БД включает весь архив знаний, включая исходные файлы. Проверка рабочего браузера и экспорта: `node scripts/live-knowledge.cjs`; она создаёт и удаляет только собственную временную сессию.

Область полноты: материалы перечисленных файлов проекта маркировки на дату снимка. Реестр источников, контрольные суммы и фактические объёмы отображаются в CRM. [План дальнейшего наполнения и проверки](KNOWLEDGE_BASE_PLAN.md).

## Первый запуск

Требуются Docker Desktop и Docker Compose. В PowerShell из папки проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/initialize.ps1 -TelegramUserIds "ВАШ_ЧИСЛОВОЙ_TELEGRAM_ID"
```

Скрипт создаёт случайные JWT_SECRET и POSTGRES_PASSWORD и не перезаписывает существующий .env. Заполните TELEGRAM_BOT_TOKEN, GOOGLE_GEMINI_API_KEY и при необходимости OPENAI_API_KEY в корневом .env. ID берётся из числового Telegram user ID, имя пользователя для разрешения доступа не подходит. Дополнительные ID задаются через запятую в TELEGRAM_ALLOWED_USER_IDS.

```powershell
docker compose up -d --build --wait
```

Или запустите start-dev.bat. Он использует Docker и не запускает второй экземпляр Telegram-бота. PostgreSQL сначала проходит healthcheck, отдельный сервис migrate применяет миграции, затем запускаются backend и frontend. Схема БД не изменяется обычным стартом backend.

Откройте панель, нажмите «Получить код в Telegram», затем «Открыть Telegram-бота». Код действует 5 минут, привязан к этому браузеру и допускает максимум 5 попыток. Перезапрос ссылки отменяет предыдущую. Вход разрешён только утверждённым ID и только в приватном чате. Сессия действует до 8 часов; выход отзывает её на сервере. Пароль мастер-доступа отсутствует.

API-ключи, .env, uploads, дампы и node_modules исключены из Git и Docker build context. Не публикуйте резервные копии и старые файлы окружения.

## Страницы веб-панели

Разделы имеют самостоятельные URL: /deals, /clients, /clients/:id, /ingest и /knowledge. Вход находится на /login. Карточка клиента открывается отдельной страницей; фильтры и номер страницы списка сохраняются в адресе. Обновление, прямые ссылки и история браузера поддерживаются.

## Telegram CRM

Отправьте /menu или /start. Клавиатура содержит загрузку переписки, клиентов, подготовку ответа, воронку, базу знаний, помощь и отдельный вход в веб. В клиентах доступны поиск, страницы, досье и последняя переписка. В карточке можно изменить статус, добавить переписку и выбрать стиль AI-ответа. Для обычного текста без режима бот уточняет действие; скриншоты одной беседы принимает пачкой. При ошибке обработки доступны кнопки повтора.

Команды: /upload, /clients, /reply, /pipeline, /knowledge, /login, /help, /cancel. Вход по коду требуется только веб-панели. Ссылка 127.0.0.1 открывает панель на компьютере, а не на телефоне; мобильный сетевой доступ требует HTTPS-адреса.

## Обновление существующей установки

При уже созданной истории миграций достаточно `docker compose up -d --build --wait`.

Если установка была создана старой версией без Prisma migrations, сначала сохраните БД и uploads. После сверки структуры существующей БД с `audit/schema-before-fixes.prisma` отметьте исходную схему как применённую:

```powershell
docker compose build
docker compose run --rm --no-deps migrate node node_modules/prisma/build/index.js migrate resolve --applied 202611090001_baseline
docker compose up -d --wait
```

Для текущей рабочей базы переход выполнен в рамках исправления. Команду resolve нельзя использовать для произвольной несовпадающей схемы. В каталоге audit сохранён исторический аудит; текущие результаты исправления описаны в FIXES.md.

POSTGRES_PASSWORD в окружении контейнера не меняет пароль уже существующей роли PostgreSQL. При ротации нужно согласованно изменить пароль роли, корневой .env и backend/.env. Нельзя просто заменить .env и рассчитывать на переинициализацию сохранённого тома. JWT_SECRET должен быть случайным и уникальным; его смена отзывает старые JWT.

## Разработка без второго polling

```powershell
cd backend
npm ci
npm run build
npm run dev
```

Во втором терминале:

```powershell
cd frontend
npm ci
npm run dev
```

backend/.env должен содержать PostgreSQL URL с адресом 127.0.0.1:5434, тот же секрет и APP_ORIGIN. TELEGRAM_POLLING=false оставляйте в локальной разработке, если бот уже работает в Docker. Не запускайте два HTTP-сервера на порту 3050. Локальный dev-сервер использует strictPort и сообщит о конфликте. В серверном боте дополнительно есть lease в БД и восстановление после ошибок polling.

## Данные и ограничения

- Импорт сохраняет клиента, диалог и первоначальную сделку в одной транзакции. Повтор идентичного импорта в тот же целевой контекст не создаёт дубль. Автопривязка использует нормализованный телефон или точный БИН; неоднозначность требует выбора клиента.
- PNG/JPEG/WebP проверяются по содержимому и перекодируются в JPEG без метаданных. До 15 изображений, до 10 МБ каждое и до 40 МБ на запрос. Максимум два одновременных запроса обработки. Загруженные файлы доступны только после входа.
- Даты сообщений сохраняются, только если распознана полная дата с часовым поясом. Исходное время остаётся в extractedInfo; дата импорта показывается отдельно.
- Списки клиентов, сделок, правил и переписки выдаются страницами; поиск клиентов выполняется на сервере. Длинная история догружается из карточки.
- Канбан включает отказ. Изменение этапа сделки обновляет статус клиента. Изменение статуса карточки обновляет последнюю сделку; IN_PROGRESS соответствует оплаченному этапу PAID.
- Контекст ИИ включает одобренные коммерческие инструкции целыми записями в пределах 12 000 символов и до шести подходящих проверенных нормативных утверждений с условиями и источниками. Старые непроверенные правила исключены. При отсутствии оснований по правовому вопросу ответ запрашивает уточнение. Фактическая модель Gemini задаётся GEMINI_MODEL; fallback указываются явно через GEMINI_FALLBACK_MODELS.
- При 429 учитывается пауза провайдера, при остальных сбоях действует ограниченное время запроса. Распознавание не выдаёт шаблон за успешно прочитанную переписку. Неудачный импорт не создаёт клиента. Восстановить исчерпанную квоту или отключённый ключ изменением приложения невозможно — это настройки аккаунта провайдера.
- `npm run seed` в backend добавляет недостающие начальные правила, не удаляя существующие записи. Редактирование существующих правил не затирается.
- Одноразовая `node dist/maintenance.js` нормализует старые телефоны, добавляет отсутствующие сделки, отключает неразрешённых старых пользователей и отзывает сессии. Непривязанные к БД файлы старше часа перемещаются в uploads/.quarantine, а не удаляются. Запускать при остановленном backend, после резервного копирования.

## Резервное копирование и восстановление

```powershell
.\backup-db.bat
.\restore-db.bat backups\crm-YYYYMMDD-HHMMSS
```

Backup временно останавливает backend для согласованного снимка, сохраняет custom-format pg_dump, uploads и контрольные суммы, затем запускает backend. Пароли и ключи храните отдельно от переносимого бэкапа.

Restore принимает каталог нового формата с manifest.json, проверяет контрольные суммы и пути, сохраняет копию текущей БД и uploads для отката. PostgreSQL восстанавливается с `--single-transaction --exit-on-error`; ошибка не выдаётся за успешный результат. Файлы заменяются при остановленном приложении. При успехе восстановленные сессии отзываются и контейнеры пересоздаются. При незавершённом восстановлении backend остаётся остановленным, чтобы не использовать несогласованные данные. Старые отдельные SQL-файлы не являются полным бэкапом: для них необходим отдельный проверенный импорт в тестовую БД и соответствующие uploads.

Том crm_pgdata содержит рабочую БД. `docker compose down -v` удаляет этот том; для обычных обновлений эта команда не нужна.

## Проверки

```powershell
npm --prefix backend run build
npm --prefix frontend run build
node scripts/test-isolated.cjs
node scripts/browser-regression.cjs
node scripts/browser-client-tools.cjs
```

В карточке клиента в вебе и Telegram есть удаление с подтверждением: удаляются карточка, сделки, переписка, AI-рекомендации и связанные скриншоты. Файлы, используемые другой карточкой, сохраняются до удаления последней ссылки. Если диск временно недоступен, файл сразу закрывается для просмотра и удаляется фоновой очередью после восстановления доступа. Резервные копии сохраняются отдельно.

Скриншоты загружайте от старой части переписки к новой. В вебе порядок можно изменить стрелками до отправки; Telegram сохраняет порядок сообщений альбома. Сообщения читаются сверху вниз по каждому изображению, совпадающие фрагменты на границе объединяются. Порядок сохраняется отдельным полем, поэтому одинаковое время импорта и переход через полночь его не меняют. Миграция восстанавливает порядок старых сообщений из сохранённого массива распознавания, где он доступен; прежние ошибки самого распознавания требуют повторной загрузки исходников.

`scripts/browser-client-tools.cjs` проверяет подтверждение удаления, обработку ошибки и фактическую отправку скриншотов в выбранном порядке; результат находится в `test-results/client-tools.json`. Дополнительная проверка `node scripts/check-screenshot-order.cjs` обращается к Gemini на синтетических изображениях и требует действующего API-ключа.

Изолированный тестовый runner поднимает отдельный PostgreSQL на случайном локальном порту, применяет миграции, выполняет проверки и удаляет только свой контейнер. Рабочую БД он не использует. Для прямого запуска backend tests нужна отдельная PostgreSQL и переменная CRM_TEST_DATABASE=1.

Браузерные проверки используют установленный Chromium. При необходимости `cd frontend; npx playwright-core install chromium`, либо задайте путь CHROMIUM_EXECUTABLE. CRM_BROWSER_URL позволяет проверить другой адрес. Запросы входа и данных в браузерных сценариях перехватываются; реальные Telegram-сообщения не отправляются. Результат сохраняется в test-results/browser.json.

## Доступ за пределами этого компьютера

По умолчанию доступ только локальный. Для внешнего или сетевого доступа нужен HTTPS reverse proxy и соответствующий APP_ORIGIN=https://ваш-домен; тогда cookie автоматически получает Secure. Публиковать backend напрямую не требуется. Настройки доверенных proxy, rate-limit store и публикации портов нужно согласовать с реальной топологией. В текущей конфигурации один backend и локальный доступ.
