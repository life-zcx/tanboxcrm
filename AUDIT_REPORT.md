# Аудит TANBOX CRM

> Исторический отчёт. Исправления и новая навигация применены 10 ноября 2026 года; текущий статус, проверки и инструкции описаны в [FIXES.md](FIXES.md).

Дата: 9 ноября 2026 года, часовой пояс Asia/Qyzylorda.

Проверены исходники frontend и backend, Prisma-схема, авторизация, Telegram-бот, AI-пайплайн, загрузка файлов, Docker/Nginx, инструкции запуска и резервного копирования. Дополнительно проверены работающие контейнеры и приложение в чистом Chromium.

Это отчёт об обнаруженных проблемах. Прикладной код, настройки работающих сервисов и содержимое CRM не исправлялись. Добавлены только материалы аудита и отдельные результаты сборки. Изменяющие данные сценарии выполнялись с подменённым хранилищем или на временном локальном сервере. Проверки работающей CRM ограничены GET/HEAD. Нагрузочные атаки и эксплуатация DoS на действующих контейнерах не проводились.

## Почему страница долго открывается и требует повторной попытки

Причин несколько. Сетевую задержку удалось воспроизвести независимо от React и ИИ.

### L1. Нестабильная передача запросов через IPv6 localhost — подтверждено

На Windows порт `[::1]:3050` обслуживает `wslrelay.exe`, а общий слушатель `[::]:3050` принадлежит `com.docker.backend.exe`. Это разные пути доступа к опубликованному Docker-порту.

В трёх сериях одинаковых HTTP-запросов:

| Адрес | HTML | JavaScript | `/api/health` |
| --- | --- | --- | --- |
| `127.0.0.1:3050` | 3–27 мс | 7–25 мс | 7–30 мс |
| `[::1]:3050` | 6–14 мс | один успех, два таймаута по 4 с | три таймаута по 4 с |

Отдельные curl-запросы через `localhost` и `::1` также завершались таймаутами через 5–10 секунд без получения HTTP-заголовков. Внутри frontend-контейнера тот же JS загружался сразу. Через IPv4 в чистом браузере вся страница входа вместе с ресурсами открылась примерно за **0,59 с**.

В браузерном запуске через `localhost` воспроизведён таймаут загрузки 15 секунд. Позднее тот же сценарий прошёл за 0,58 с: дефект **плавающий**. В прежних access-логах браузера встречаются паузы около 30 секунд между HTML, JS и CSS, что согласуется с сетевыми ожиданиями, но access-лог без `$request_time` не позволяет точно измерить длительность каждого прошлого запроса.

**Вывод:** в проверенной среде воспроизводится проблема IPv6-пути Windows/WSL/Docker. Конкретный внутренний дефект `wslrelay` или Docker до уровня сетевого драйвера не установлен. Сводить проблему только к React, ИИ или размеру JS оснований нет.

**Рабочий обход:** открывать [http://127.0.0.1:3050](http://127.0.0.1:3050). У этого адреса отдельное браузерное хранилище, поэтому потребуется заново войти. Для постоянного решения — проверить публикацию порта и маршрутизацию localhost в Docker Desktop/WSL. Для локальной CRM можно явно публиковать frontend на `127.0.0.1:3050:3050`, а backend сделать доступным только в Docker-сети. Если нужен доступ из локальной сети, адрес публикации следует выбрать с учётом этого требования.

Доказательства: [network-results.json](audit/network-results.json), [network-check.cjs](audit/network-check.cjs). Назначение `wslrelay.exe` описано в [документации Microsoft WSL](https://github.com/microsoft/WSL/blob/master/doc/docs/technical-documentation/localhost.md).

### L2. Любой сбой проверки сессии удаляет вход — подтверждено в браузере

`frontend/src/api.ts:144` преобразует любой HTTP-ответ с ошибкой в `Unauthorized`, включая `500`, `502`, `503`. `frontend/src/App.tsx:47` удаляет токен при любой ошибке, в том числе таймауте и обрыве сети.

Изолированная подстановка `503` для API привела к удалению сохранённого токена и показу формы входа. Поэтому временная задержка или старт backend превращаются в потерю сессии.

**Исправление:** удалять сессию только после подтверждённого отказа авторизации; сетевые ошибки и `5xx` показывать с повтором запроса, сохраняя токен. Проверять сессию до загрузки защищённых данных.

### L3. Ошибки API отображаются как пустая CRM — подтверждено в браузере

`frontend/src/api.ts:173,217` возвращает пустые списки при `5xx`. `frontend/src/App.tsx:62,66` дополнительно перехватывает ошибки, включая `401`, и снова заменяет их пустыми списками. Внешний обработчик `Unauthorized` в `loadData()` практически не получает эти ошибки.

При ответах `500` браузер показал пять колонок «Нет сделок на этом этапе», без сообщения об ошибке. Это легко принять за незагрузившуюся страницу или пропавшие данные. Автоповтора и видимой кнопки восстановления нет.

**Исправление:** различать пустые данные и ошибку загрузки; единообразно проверять HTTP-статусы; показывать ошибку и действие «Повторить»; не затирать прежние данные пустыми массивами после временного сбоя.

### L4. Nginx возвращает HTML вместо отсутствующего JS — условие воспроизведено

`frontend/nginx.conf:15` применяет `try_files ... /index.html` ко всем путям, включая `/assets/*.js`. Если HTML ссылается на удалённый файл предыдущей сборки, Nginx отвечает `200 text/html`. Браузер отклоняет модуль и React не запускается.

В тесте с отсутствующим asset получена ошибка `Failed to load module script ... MIME type "text/html"`, контейнер `#root` остался пустым. Это подтверждает дефект конфигурации. Наличие именно такой ошибки в прошлой пользовательской консоли не установлено: непосредственного доступа к её истории нет.

**Исправление:** отдельный `location /assets/` с `try_files $uri =404`; явная политика кеша для HTML и хешированных ресурсов; согласованное обновление сборки. Поведение `try_files` описано в [документации Nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files).

### L5. Автоматический ввод кода входа использует старое значение — подтверждено в браузере

`frontend/src/components/LoginPage.tsx:34` вызывает `setCode(val)`, затем таймер вызывает `handleSubmit()` из предыдущего рендера. При вводе шестой цифры обработчик видит пятизначный код, при вставке полного кода может видеть пустую строку.

В тесте после ввода и вставки шести цифр запрос не отправлялся; появлялась локальная ошибка. Отдельное нажатие кнопки отправляло правильный код. Если до этого в поле был другой полный код, таймер может отправить его.

**Исправление:** передавать актуальный `val` в функцию проверки и предотвращать параллельную отправку. Причина соответствует модели состояния React: обработчики используют [состояние своего рендера](https://react.dev/learn/state-as-a-snapshot).

### L6. Frontend не ждёт готовности API — подтверждено конфигурацией

`docker-compose.yml:52` ждёт только запуска контейнера backend. Сам backend сначала выполняет `prisma db push` и генерацию клиента (`backend/Dockerfile:12`). Его healthcheck отсутствует. `/api/health` в `backend/src/server.ts:33` не проверяет БД. В `start-dev.bat` вместо проверки готовности стоит фиксированная задержка 2 секунды.

Это создаёт окно, когда интерфейс уже открыт, а API ещё недоступен. В сочетании с L2/L3 оно приводит к выходу из сессии или пустой доске. Перезапуск сервисов для искусственного воспроизведения этого окна не выполнялся.

**Исправление:** добавить readiness-проверку API и БД, `condition: service_healthy` для frontend, убрать миграцию схемы из обычного старта приложения. Compose сам по себе [не ждёт готовности сервиса](https://docs.docker.com/compose/how-tos/startup-order/).

## Критические уязвимости

### C1. Постоянный код полного доступа

`backend/src/modules/auth/auth.controller.ts:89` принимает постоянный шестизначный мастер-код и `ADMIN_API_KEY` вместо действующего одноразового кода. Резервная ветка создаёт/обновляет администратора и выдаёт JWT на семь дней.

**Доказательство:** при отсутствии любого OTP в подменённом хранилище контроллер вернул `200` и токен. В работающей CRM этот сценарий не запускался, чтобы не менять пользователей и время входа.

**Исправление:** удалить мастер-вход. Организовать отдельное контролируемое восстановление доступа. После устранения остальных путей обхода сменить секрет JWT и завершить старые сессии.

### C2. Любой пользователь Telegram получает ADMIN и доступ к клиентам

`backend/src/bot/telegram.bot.ts:60,90` без allowlist или подтверждения владельцем создаёт администратора для `/start`, `/login`, `/code`. Команды `/clients`, обработчики досье, текста, изображений и AI-кнопок тоже не защищены. Доступ определяется `ctx.chat.id`, а не разрешённым `ctx.from.id`; в группе код может оказаться видимым всем участникам.

**Доказательство:** синтетический update `/login` от незарегистрированного пользователя создал роль `ADMIN` и вызвал отправку OTP через подменённый транспорт.

**Исправление:** единый middleware проверки разрешённых Telegram user ID до всех обработчиков; вход только в приватном чате; предварительно одобренные учётные записи; проверка прав на чтение и изменение CRM. Имя Telegram не должно служить идентификатором доверия.

### C3. Стандартный JWT-секрет позволяет подделывать доступ

`backend/src/config/env.ts:12` и `docker-compose.yml:33` содержат предсказуемое значение по умолчанию. В работающем backend используется именно оно. `backend/src/middleware/auth.middleware.ts:28` после проверки подписи доверяет payload, не проверяя существование и действующие права пользователя.

**Доказательство на работающей CRM:** JWT с вымышленным ID, подписанный стандартным секретом, получил `200` на `/api/clients/stats/summary`, тогда как `/api/auth/me` для него вернул `401`. Проверка была только на чтение.

**Исправление:** обязательный случайный секрет без fallback, отказ запуска со стандартным значением, проверка действующего пользователя и прав, механизм отзыва сессий. Ротация одного секрета не устранит C1 и C2.

| ID | Проблема | Где и что сделать |

Дополнительно:

- Большинство frontend-методов изменения данных (`api.ts:181–292`) не проверяет `res.ok`. HTTP-ошибка может выглядеть как успешное перемещение сделки, сохранение статуса или регламента. Оптимистическое обновление не откатывается на обычный `4xx/5xx`.
- Ошибки Prisma возвращаются клиенту через `error.message`. Общего обработчика ошибок и нормальной схемы валидации запросов нет. Строковые статусы/категории не ограничены перечислениями; числовые поля могут принимать некорректные значения и давать `500` вместо `400`.
- `requestCode()` сообщает `sent: true`, даже если `sendAuthCode()` вернул `false`. Уведомление о выдаче кода поэтому может быть ложным.
- `/api/ai/status` сообщает фиксированную модель `gemini-2.0-flash`, которая отличается от фактической конфигурации/fallback. Sidebar всегда рисует зелёный статус бота, `App` не загружает AIStatus, а текущий Header его не использует.
- Ввод из OCR/LLM приводится к TypeScript-интерфейсу без проверки реального JSON. Чужие инструкции в переписке могут повлиять на распознаваемые поля и AI-ответы. Нужны проверка схемы результата и отделение недоверенного содержания от инструкций. Выполнения серверных команд или автоматической отправки AI-ответов клиентам в исследованном коде нет.
- Код сохраняет время импорта вместо распознанного времени сообщения. Из-за этого история выглядит хронологической, но не отражает реальные даты переписки.
- Выход удаляет локальный токен, но не отзывает JWT на сервере; срок жизни — семь дней. В сочетании с H1 это увеличивает последствия кражи токена.
- `cors` настроен как `origin: '*'` вместе с `credentials: true`. Это не заменяет авторизацию и не ограничивает origin. Для выбранного способа входа нужно настроить согласованную CORS-политику, не полагаясь на неё как на защиту API.
- Нет существующего набора тестов, lint-скриптов и CI в представленном дереве. Git-репозитория в этой папке также нет, поэтому история изменений и прежние утечки секретов не проверялись.

## Порядок исправления

1. Закрыть три независимых обхода входа: мастер-код, открытую регистрацию ADMIN в Telegram, стандартный JWT-секрет. Проверить разрешённых пользователей и завершить старые сессии.
2. Закрыть активные загрузки и публичную выдачу скриншотов; ограничить поля обновления; усилить OTP; обновить Multer с учётом актуальных advisories.
3. Устранить риск удаления/неполного восстановления: безопасный seed, документация, stop-on-error и резервное копирование вместе с uploads.
4. Для немедленной работы использовать `127.0.0.1:3050`; затем устранить нестабильность IPv6-публикации, настроить readiness, разделить сетевые ошибки и отказ входа, добавить явный повтор загрузки.
5. Исправить автоматическую отправку кода, выдачу отсутствующих assets и обработку HTTP-ошибок во всех frontend-методах.
6. Исправить очередь Telegram, Markdown, состояния polling/ИИ и атомарность импорта; затем создание сделок, базу знаний и синхронизацию статусов.

Сетевой дефект подтверждён для текущей Windows/Docker-среды; его переносимость на иной сервер не предполагается. Автоматическая проверка не доказывает отсутствие других уязвимостей.
